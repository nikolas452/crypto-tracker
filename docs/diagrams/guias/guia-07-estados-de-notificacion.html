Estados de una notificación en la cola de correos (outbox)

Qué responde este diagrama: por qué estados pasa cada correo desde que se anota hasta que se envía o falla, y qué reintentos o acciones intervienen.

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

Outbox (cola de correos)
La colección notifications: una fila por correo pendiente. Se escribe junto con la alerta y otro proceso la vacía después.
dedupeKey
La clave única alertId:triggerCount de cada notificación. Impide crear dos correos para el mismo disparo.
Backoff
Una espera creciente entre reintentos: 1, 5, 15 y 60 minutos, con una variación aleatoria de ±10 %.
SMTP y Mailpit
SMTP es el protocolo de envío de correo. En local se usa Mailpit, un buzón de mentira: recibe por el puerto 1025 y se ve en http://localhost:8025.
Worker
El programa que trabaja por reloj (npm run dev:worker, src/worker.ts). Es la cocina: nadie le pide nada, prepara las cosas solo. No tiene servidor HTTP.

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    Nace pending

    Lo dispara: Backend solo

    La fila se crea en la misma transacción que dispara la alerta, con attempts: 0, maxAttempts: 5 y nextAttemptAt igual al momento del disparo. Su dedupeKey es alertId:triggerCount: es única, así que un mismo disparo no genera dos correos.

    MongoDB
    Escribe notifications.
    Código
    src/jobs/alertEvaluation.ts src/modules/notifications/notifications.model.ts
  2. 2

    pending → sending (claimNext)

    Lo dispara: Backend solo

    send-notifications reclama de forma atómica la pending más antigua cuyo nextAttemptAt ya venció y la deja sending, con lockedAt y lockedBy. Ningún otro proceso puede tomarla.

    MongoDB
    Escribe notifications.
    Código
    src/modules/notifications/notifications.service.ts
  3. 3

    sending → sent

    Lo dispara: Backend solo

    Cuando el servidor SMTP acepta el mensaje, la fila queda sent con sentAt y providerMessageId. "Aceptado" significa que el SMTP lo recibió; no garantiza que el usuario lo haya leído.

    MongoDB
    Escribe notifications.
    Código
    src/jobs/sendNotifications.ts
  4. 4

    sending → pending (reintento con espera)

    Lo dispara: Backend solo

    Un fallo transitorio (SMTP_UNAVAILABLE: sin conexión, timeout o respuesta 4xx, o un error inesperado) suma un intento y vuelve a pending con nextAttemptAt a 1, 5, 15 o 60 minutos (variación aleatoria de ±10 %). Se guarda lastError (code, message y permanent, nunca un stack).

    MongoDB
    Escribe notifications (attempts, nextAttemptAt, lastError).
    Código
    src/jobs/sendNotifications.ts src/jobs/notifyBackoff.ts
  5. 5

    sending → failed

    Lo dispara: Backend solo

    Termina en failed si el SMTP rechaza de forma permanente (SMTP_REJECTED, respuestas 5xx) o si se alcanzan los 5 intentos. Es un estado final: nada lo reintenta solo.

    MongoDB
    Escribe notifications.
    Código
    src/jobs/sendNotifications.ts src/integrations/mailer/mailer.errors.ts
  6. 6

    sending → cancelled (el usuario ya no existe)

    Lo dispara: Backend solo

    Antes de enviar, el job comprueba que el usuario todavía exista. Si no, marca la notificación cancelled y no manda nada.

    MongoDB
    Lee users; escribe notifications.
    Código
    src/jobs/sendNotifications.ts
  7. 7

    Un lock viejo se recupera solo

    Lo dispara: Backend solo

    Si un worker murió a mitad de un envío, la fila queda sending. En su próxima corrida, send-notifications recupera las que llevan más de 10 minutos (NOTIFY_LOCK_TIMEOUT_MIN): vuelven a pending con un intento más, o pasan a failed si eso agota los 5.

    MongoDB
    Escribe notifications.
    Código
    src/modules/notifications/notifications.service.ts src/jobs/sendNotifications.ts
  8. 8

    pending → cancelled (el cliente borra la alerta)

    Lo dispara: Cliente

    Al borrar una alerta con DELETE /api/v1/me/alerts/:id, sus notificaciones pending pasan a cancelled. Nunca toca una que ya esté sending. (Si el cliente borra su cuenta con DELETE /api/v1/me, sus notificaciones se borran directamente, salvo las sending.)

    MongoDB
    Escribe notifications.
    Código
    src/modules/notifications/notifications.service.ts src/modules/alerts/alerts.service.ts
  9. 9

    failed → pending (retry de un administrador)

    Lo dispara: Ambos

    POST /api/v1/admin/notifications/:id/retry devuelve una failed a pending con attempts: 0 y nextAttemptAt ahora; sobre una que no esté failed responde 409. El administrador lo pide, pero el envío lo hace el worker en su próxima corrida (cada minuto): por eso es "Ambos".

    MongoDB
    Escribe notifications.
    Código
    src/modules/notifications/notifications.admin.service.ts
  10. 10

    Consultar el historial

    Lo dispara: Cliente

    GET /api/v1/me/notifications (filtro ?status=) muestra al usuario sus notificaciones, con el correo enmascarado y solo el code del último error. Los administradores ven el detalle completo en GET /api/v1/admin/notifications.

    MongoDB
    Lee notifications.
    Código
    src/modules/notifications/notifications.routes.ts src/modules/notifications/notifications.admin.routes.ts

Cómo verlo en tu entorno

  • Levanta lo básico: docker compose up (MongoDB como replica set y Mailpit), luego npm run dev (la API queda en http://localhost:3000) y, en otra terminal, npm run dev:worker.
  • Mailpit: abre http://localhost:8025 para ver los correos que envía el worker (recibe por SMTP en el puerto 1025).
  • Como usuario: My Notifications → List my notification history y List my notifications - filtered by status (?status=failed).
  • Como admin: Admin - Notifications → List notifications (full diagnostic detail), Retry a failed notification, Retry a non-failed notification -> 409 y Send an immediate test email (este último va directo por SMTP, sin pasar por la cola).
  • Para provocar un fallo transitorio, detén Mailpit (docker compose stop mailpit) mientras se dispara una alerta y observa los reintentos y lastError.code.
  • Logs del worker: en la terminal de npm run dev:worker aparecen líneas como Worker started, poll-prices run started / poll-prices run finished y send-notifications: sent.
