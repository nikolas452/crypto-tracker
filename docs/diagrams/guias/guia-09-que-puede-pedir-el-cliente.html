Qué puede pedir el cliente a la API y qué datos toca

Qué responde este diagrama: qué endpoints puede pedir cada tipo de cliente (sin login, usuario con token y administrador) y contra qué datos de MongoDB trabaja cada grupo.

Idea clave (el mostrador y la cocina): la API es el mostrador. Solo responde cuando alguien pide algo y siempre trabaja con lo que ya está guardado en MongoDB. Quien cocina los precios y manda los correos es el worker, y eso se ve en la guía 10.

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

Cliente
Cualquier programa que llame a la API: una web, una app o Postman. En este proyecto todavía no hay front end.
API
El programa que atiende pedidos HTTP (npm run dev, src/server.ts). Es el mostrador: recibe pedidos, responde y no cocina nada por su cuenta.
Endpoint
Una dirección de la API con un verbo HTTP, por ejemplo GET /api/v1/coins.
Token de Firebase (JWT)
La credencial que el cliente obtiene de Firebase Auth y envía en Authorization: Bearer <token>. La API lo verifica con Firebase.
Firebase Auth
El servicio externo que emite y verifica las identidades. La API no guarda contraseñas.
MongoDB
La base de datos. Es el único lugar donde se encuentran API y worker: el worker deja cosas ahí y la API las lee.
Límite de tasa
Un tope de pedidos por ventana de tiempo. Si se supera, la API responde 429 RATE_LIMITED.

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    Sin login: precios y estado (nodo 1 del diagrama)

    Lo dispara: Cliente

    Cualquiera puede consultar GET /api/v1/coins (lista con page, limit, sort, order y q), GET /api/v1/coins/:coingeckoId, /history, /stats y GET /api/v1/status. Fuera de /api también hay GET /health y GET /health/ready. Todo es lectura: la API no llama a CoinGecko para responder, lee lo que el worker ya guardó. Las respuestas de /coins llevan Cache-Control: public, max-age=60 y la de /status lleva no-store.

    MongoDB
    Lee coins (incluye latest), price_snapshots (history y stats), y para /status: job_runs, agenda_jobs y el conteo de coins activas. No escribe nada.
    Código
    src/app.ts src/modules/coins/coins.routes.ts src/modules/status/status.service.ts
  2. 2

    Usuario con token: perfil y watchlist (nodo 2)

    Lo dispara: Cliente

    Con Authorization: Bearer <token> de Firebase, el usuario usa GET/PATCH/DELETE /api/v1/me (solo se edita displayName) y /api/v1/me/watchlist (GET, POST, PATCH /:coingeckoId, DELETE /:coingeckoId). Agregar a la watchlist no llama a CoinGecko: busca la moneda en la colección local coins (debe existir y estar activa) y respeta el tope WATCHLIST_MAX_ITEMS (50). Listar la watchlist hace un $lookup a coins y devuelve coins.latest.

    MongoDB
    Lee y escribe users (el primer pedido con token crea el perfil con rol user) y watchlist_items. Lee coins.
    Código
    src/modules/users/users.routes.ts src/modules/watchlist/watchlist.service.ts src/middlewares/requireAuth.ts
  3. 3

    Usuario con token: alertas y avisos (nodo 3)

    Lo dispara: Cliente

    /api/v1/me/alerts permite GET, POST, GET /:id, PATCH /:id y DELETE /:id. GET /api/v1/me/notifications (con ?status=) solo lista. Crear una alerta exige email verificado (422 EMAIL_NOT_VERIFIED), moneda activa (404) y no pasar de ALERTS_MAX_ACTIVE (20, 422 LIMIT_REACHED). La alerta se guarda como armed y no se evalúa en ese momento: la respuesta solo informa meta.currentValue y meta.conditionCurrentlyMet. Quién la evalúa después es el worker.

    MongoDB
    Escribe alerts; lee coins y notifications. Al borrar una alerta, sus notificaciones pending pasan a cancelled.
    Código
    src/modules/alerts/alerts.service.ts src/modules/notifications/notifications.routes.ts
  4. 4

    Administrador (nodo 4)

    Lo dispara: Ambos

    Bajo /api/v1/admin hacen falta token no revocado y rol admin: job-runs (GET lista y detalle), jobs (GET, POST /:name/run, /disable, /enable), coins (GET, POST, PATCH /:coingeckoId) y notifications (GET, POST /:id/retry, POST /test-email). Ojo: run solo encola el job con agenda.now y responde 202; el worker es quien lo ejecuta unos segundos después (el cliente lo pide, el backend lo hace: por eso es "Ambos"). Repite antes de 30 s y responde 429; con el job deshabilitado responde 409. POST /admin/coins valida el id contra CoinGecko: es el único caso en que la API llama a CoinGecko. test-email envía por SMTP directo al correo del propio admin, sin pasar por la cola.

    MongoDB
    Lee job_runs, agenda_jobs, coins y notifications. Escribe agenda_jobs (encolar, deshabilitar), coins.isActive y notifications (retry: failed vuelve a pending).
    Código
    src/app.ts src/modules/jobs/jobs.admin.routes.ts src/modules/coins/coins.admin.service.ts src/modules/notifications/notifications.admin.service.ts
  5. 5

    Borrar la cuenta (efecto en cadena)

    Lo dispara: Cliente

    DELETE /api/v1/me exige token no revocado y borra, en este orden, las notificaciones del usuario (salvo las que estén sending), sus alertas, su watchlist y su perfil. La cuenta de Firebase no se borra: el siguiente pedido con ese token vuelve a crear un perfil vacío.

    MongoDB
    Borra en notifications, alerts, watchlist_items y users.
    Código
    src/modules/users/users.service.ts

Cómo verlo en tu entorno

  • Levanta lo básico: docker compose up (MongoDB como replica set y Mailpit), luego npm run dev (la API queda en http://localhost:3000) y, en otra terminal, npm run dev:worker.
  • Importa crypto-tracker.postman_collection.json en Postman (variable baseUrl) o abre requests.http con la extensión REST Client de VS Code; ambos traen los mismos pedidos. Carpetas relevantes: Coins, Status, Me, My Watchlist, My Alerts, My Notifications y Admin - Jobs / Admin - Coins / Admin - Notifications.
  • Para las rutas con token: en Postman, carpeta Auth (Firebase), pedido Sign in (get ID token) (o npm run auth:token). Para las de admin, promueve al usuario con npm run user:set-role -- --email ... --role admin.
  • Prueba el "solo encola": en Admin - Jobs, pedido Trigger a job now responde 202 al instante; el resultado real aparece después en Admin - Job Runs y en los logs del worker.
  • GET /api/v1/status (Postman: carpeta Status, pedido Worker status) muestra activeCoins y, en pollPrices: lastRunAt, lastRunStatus, lastSuccessAt, stale, nextRunAt y disabled.
