Contexto del sistema: procesos y servicios del backend

Qué responde este diagrama: qué procesos y servicios forman el backend y quién habla con quién.

Idea clave: hay dos procesos que nunca se hablan directamente. La API (el mostrador) y el worker (la cocina) se comunican solo a través de MongoDB. Si quieres ver el reparto entre lo que dispara el cliente y lo que ocurre solo, empieza por las guías 09, 10 y 11.

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

API
El programa que atiende pedidos HTTP (npm run dev, src/server.ts). Es el mostrador: recibe pedidos, responde y no cocina nada por su cuenta.
Worker
El programa que trabaja por reloj (npm run dev:worker, src/worker.ts). Es la cocina: nadie le pide nada, prepara las cosas solo. No tiene servidor HTTP.
MongoDB
La base de datos. Es el único lugar donde se encuentran API y worker: el worker deja cosas ahí y la API las lee.
Agenda
La librería que dispara los jobs a su hora. Guarda su agenda en la colección agenda_jobs de MongoDB y la revisa cada pocos segundos (AGENDA_PROCESS_EVERY, 10 s).
Firebase Auth
El servicio externo que emite y verifica las identidades. La API no guarda contraseñas.
SMTP y Mailpit
SMTP es el protocolo de envío de correo. En local se usa Mailpit, un buzón de mentira: recibe por el puerto 1025 y se ve en http://localhost:8025.
Cliente
Cualquier programa que llame a la API: una web, una app o Postman. En este proyecto todavía no hay front end.

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    El cliente y el administrador llaman a la API

    Lo dispara: Cliente

    Un cliente (o un administrador con rol admin) hace pedidos HTTP a /api/v1 o /api/v1/admin. La API es npm run dev (src/server.ts, Express, puerto PORT = 3000 por defecto). Solo atiende pedidos: nunca ejecuta jobs.

    MongoDB
    Ninguna por sí mismo; según la ruta lee o escribe (paso siguiente).
    Código
    src/server.ts src/app.ts
  2. 2

    La API verifica el token con Firebase

    Lo dispara: Cliente

    Las rutas /me/* y /admin/* exigen un token de Firebase que requireAuth verifica con Firebase Auth. Las rutas /coins y /status son públicas y no consultan a Firebase.

    MongoDB
    Lee y escribe users (crea el perfil en el primer pedido).
    Código
    src/middlewares/requireAuth.ts src/integrations/firebase/tokenVerifier.ts
  3. 3

    La API lee y escribe en MongoDB

    Lo dispara: Cliente

    Responde con lo que hay guardado y escribe lo que el usuario pide (watchlist, alertas, perfil). Para las acciones de admin sobre jobs no ejecuta nada: encola un documento en agenda_jobs (rol producer de Agenda) y el worker lo ejecuta. Dos excepciones concretas en las que la API sale a un servicio externo: POST /admin/coins valida el id contra CoinGecko y POST /admin/notifications/test-email envía un correo de prueba por SMTP.

    MongoDB
    users, watchlist_items, alerts, notifications, coins, agenda_jobs (según la ruta).
    Código
    src/app.ts src/scheduler/agenda.ts
  4. 4

    El worker consulta CoinGecko

    Lo dispara: Backend solo

    El worker (npm run dev:worker, src/worker.ts) no tiene servidor HTTP. Cada 10 minutos su job poll-prices pide los precios a CoinGecko con COINGECKO_API_KEY.

    MongoDB
    Lee coins (las monedas activas).
    Código
    src/worker.ts src/integrations/coingecko/coingecko.client.ts
  5. 5

    El worker guarda precios y estado de jobs en MongoDB

    Lo dispara: Backend solo

    Guarda snapshots y coins.latest, evalúa alertas, registra cada corrida en job_runs y usa agenda_jobs y job_locks para coordinarse. MongoDB debe ser replica set porque las alertas usan transacciones (API y worker lo verifican al arrancar).

    MongoDB
    price_snapshots, coins, alerts, notifications, job_runs, job_locks, agenda_jobs.
    Código
    src/jobs/pollPrices.ts src/lib/verifyReplicaSet.ts
  6. 6

    El worker envía los correos por SMTP

    Lo dispara: Backend solo

    El job send-notifications toma las notificaciones pending y las envía por SMTP (Mailpit en local). Es el único canal por el que el backend le avisa algo al usuario por su cuenta.

    MongoDB
    Lee y escribe notifications.
    Código
    src/jobs/sendNotifications.ts src/integrations/mailer/smtpMailer.ts
  7. 7

    Los scripts CLI cargan datos

    Lo dispara: Backend solo

    Scripts que ejecuta una persona desde la terminal, sin pasar por la API: npm run seed:coins (carga el catálogo), npm run backfill:history, npm run coins:rebuild-latest, npm run job:poll-prices (una corrida suelta), npm run auth:create-test-user, npm run auth:token y npm run user:set-role. No los dispara ningún cliente HTTP.

    MongoDB
    Escriben directo en coins, price_snapshots y users, según el script.
    Código
    src/scripts/seedCoins.ts src/scripts/backfillHistory.ts src/scripts/setRole.ts

Cómo verlo en tu entorno

  • Levanta lo básico: docker compose up (MongoDB como replica set y Mailpit), luego npm run dev (la API queda en http://localhost:3000) y, en otra terminal, npm run dev:worker.
  • Comprueba que la API vive: GET /health y GET /health/ready (Postman: carpeta Health). El segundo verifica la conexión a MongoDB y responde 503 si está caída.
  • Carga el catálogo antes de nada con npm run seed:coins; sin monedas activas, poll-prices termina en skipped.
  • GET /api/v1/status (Postman: carpeta Status, pedido Worker status) muestra activeCoins y, en pollPrices: lastRunAt, lastRunStatus, lastSuccessAt, stale, nextRunAt y disabled.
  • Mailpit: abre http://localhost:8025 para ver los correos que envía el worker (recibe por SMTP en el puerto 1025).
