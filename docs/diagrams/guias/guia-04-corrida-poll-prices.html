Una corrida del job poll-prices y cómo termina

Qué responde este diagrama: qué pasos ejecuta una corrida de poll-prices, en qué orden, y con qué estado final puede terminar.

Idea clave: el job nunca "explota". Cualquier problema se convierte en un estado final registrado en job_runs, y lo que ya se guardó (snapshots) se conserva.

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

Job
Una tarea del worker con nombre propio: poll-prices, send-notifications o maintenance. Su lógica está en src/jobs/*.
Lease
Un candado con vencimiento (colección job_locks, 5 minutos) que evita que dos corridas de poll-prices trabajen a la vez.
job_runs
El libro de registro de los jobs: cada corrida deja una fila con su estado (running, success, partial, failed, skipped), duración y contadores.
Snapshot
Una "foto" del precio de una moneda en un momento. Se guardan en price_snapshots y expiran a los 90 días.
coins.latest
El último precio copiado dentro de cada documento de coins, para responder rápido sin recorrer el historial.
Alerta
Una regla del usuario, por ejemplo "avisar si bitcoin baja de cierto precio". Vive en la colección alerts y tiene un estado (armed, triggered, completed, disabled).
Estados de una corrida
success: todo bien. partial: hubo un fallo parcial. failed: no se logró nada. skipped: no correspondía correr.
Agenda
La librería que dispara los jobs a su hora. Guarda su agenda en la colección agenda_jobs de MongoDB y la revisa cada pocos segundos (AGENDA_PROCESS_EVERY, 10 s).

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    Llega el disparo

    Lo dispara: Ambos

    La corrida la dispara el cron cada 10 minutos (trigger: "agenda"), el arranque del worker ("startup"), un administrador ("api", el cliente pide y el worker ejecuta) o el reintento automático ("retry"). El adaptador de Agenda es quien continúa con el paso siguiente.

    MongoDB
    Lee agenda_jobs.
    Código
    src/scheduler/adapters.ts src/scheduler/definitions.ts
  2. 2

    Tomar el lease

    Lo dispara: Backend solo

    Intenta tomar el lease poll-prices con vencimiento a los 5 minutos (POLL_LOCK_TTL_MS). Si otro dueño lo tiene, registra una fila skipped con skipReason: "locked" y termina sin llamar a CoinGecko.

    MongoDB
    Escribe job_locks; en el caso ocupado, escribe job_runs (skipped).
    Código
    src/lib/lease-lock.ts src/scheduler/adapters.ts
  3. 3

    Abrir la corrida

    Lo dispara: Backend solo

    Crea la fila de job_runs en estado running, con trigger, startedAt y workerId.

    MongoDB
    Escribe job_runs.
    Código
    src/jobs/pollPrices.ts src/modules/job-runs/job-runs.service.ts
  4. 4

    Leer las monedas activas

    Lo dispara: Backend solo

    Lee todas las monedas con isActive: true. Si no hay ninguna, cierra la corrida como skipped con skipReason: "no_active_coins".

    MongoDB
    Lee coins.
    Código
    src/jobs/pollPrices.ts
  5. 5

    Pedir precios a CoinGecko

    Lo dispara: Backend solo

    Pide los precios en lotes de hasta 50 ids. Si la llamada falla (por ejemplo COINGECKO_UNAVAILABLE, COINGECKO_RATE_LIMITED o COINGECKO_AUTH), la corrida cierra como failed. Si CoinGecko responde pero no devuelve ninguna moneda pedida, cierra como failed con COINGECKO_NO_COINS_RETURNED.

    MongoDB
    Ninguna en este paso.
    Código
    src/jobs/pollPrices.ts src/integrations/coingecko/coingecko.client.ts
  6. 6

    Guardar snapshots

    Lo dispara: Backend solo

    Compara sourceUpdatedAt con el último guardado de cada moneda; las que no cambiaron se omiten (skippedUnchanged) y las demás se insertan.

    MongoDB
    Lee y escribe price_snapshots.
    Código
    src/jobs/pollPrices.ts src/modules/snapshots/snapshots.service.ts
  7. 7

    Refrescar coins.latest

    Lo dispara: Backend solo

    Actualiza coins.latest de las monedas con snapshot nuevo. Si falla, la corrida se degrada a partial con el código LATEST_UPDATE_FAILED; los snapshots ya insertados se conservan.

    MongoDB
    Escribe coins.latest.
    Código
    src/jobs/pollPrices.ts
  8. 8

    Evaluar alertas

    Lo dispara: Backend solo

    Evalúa las alertas armed y triggered solo de las monedas con snapshot nuevo (ver guía 05). Si la evaluación lanza una excepción inesperada, la corrida se degrada a partial con ALERT_EVALUATION_FAILED.

    MongoDB
    Lee y escribe alerts; escribe notifications.
    Código
    src/jobs/alertEvaluation.ts
  9. 9

    Cerrar con su estado final y liberar el lease

    Lo dispara: Backend solo

    success: ninguna moneda faltó y no hubo errores (aunque todas se hayan omitido por no cambiar). partial: faltaron algunas monedas en la respuesta, o falló coins.latest o la evaluación de alertas. failed: no llegó ningún precio o hubo un error inesperado. skipped: lease ocupado o sin monedas activas. El lease se libera siempre, incluso si falló.

    MongoDB
    Actualiza job_runs (estado, duración, contadores, error) y borra el lease de job_locks.
    Código
    src/jobs/pollPrices.ts src/scheduler/adapters.ts
  10. 10

    Si se disparó alguna alerta, despertar a send-notifications

    Lo dispara: Backend solo

    Si la corrida no terminó en failed y alertsTriggered es mayor que 0, encola send-notifications de inmediato con agenda.now, sin esperar su resultado.

    MongoDB
    Escribe agenda_jobs (documento puntual).
    Código
    src/jobs/pollPrices.ts src/worker.ts
  11. 11

    Reintento automático (solo casos transitorios)

    Lo dispara: Backend solo

    Solo si la corrida terminó en failed con COINGECKO_UNAVAILABLE o COINGECKO_RATE_LIMITED, se agenda un reintento a los 2 minutos, una sola vez (POLL_MAX_JOB_RETRIES = 1), salvo que la próxima corrida regular esté a menos de 3 minutos. COINGECKO_AUTH, COINGECKO_NO_COINS_RETURNED e INTERNAL no se reintentan, y una corrida partial tampoco.

    MongoDB
    Escribe agenda_jobs (job puntual con trigger: "retry").
    Código
    src/scheduler/retryPolicy.ts

Cómo verlo en tu entorno

  • Levanta lo básico: docker compose up (MongoDB como replica set y Mailpit), luego npm run dev (la API queda en http://localhost:3000) y, en otra terminal, npm run dev:worker.
  • Ejecuta una corrida: Admin - Jobs → Trigger a job now (202, solo encola) o npm run job:poll-prices (una corrida directa, sin worker).
  • Mira el resultado: Admin - Job Runs → List job runs (filtered by jobName + date range) con jobName=poll-prices; abre una con Job run detail para ver status, skipReason, error y stats.
  • Provoca un skipped: desactiva todas las monedas (Admin - Coins → Deactivate a coin) y dispara otra corrida.
  • Logs del worker: en la terminal de npm run dev:worker aparecen líneas como Worker started, poll-prices run started / poll-prices run finished y send-notifications: sent.
  • GET /api/v1/status (Postman: carpeta Status, pedido Worker status) muestra activeCoins y, en pollPrices: lastRunAt, lastRunStatus, lastSuccessAt, stale, nextRunAt y disabled.
