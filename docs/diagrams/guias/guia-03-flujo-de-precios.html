Cómo llega un precio de CoinGecko hasta la API

Qué responde este diagrama: por qué camino viaja un precio desde CoinGecko hasta la respuesta JSON que recibe el cliente, y quién escribe y quién lee en cada tramo.

Idea clave: el precio nunca va "en vivo" de CoinGecko al cliente. El worker lo baja cada 10 minutos, lo guarda en MongoDB y la API solo lee lo guardado. Por eso un cliente puede ver un precio de hace unos minutos.

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

Worker
El programa que trabaja por reloj (npm run dev:worker, src/worker.ts). Es la cocina: nadie le pide nada, prepara las cosas solo. No tiene servidor HTTP.
MongoDB
La base de datos. Es el único lugar donde se encuentran API y worker: el worker deja cosas ahí y la API las lee.
Snapshot
Una "foto" del precio de una moneda en un momento. Se guardan en price_snapshots y expiran a los 90 días.
coins.latest
El último precio copiado dentro de cada documento de coins, para responder rápido sin recorrer el historial.
job_runs
El libro de registro de los jobs: cada corrida deja una fila con su estado (running, success, partial, failed, skipped), duración y contadores.
API
El programa que atiende pedidos HTTP (npm run dev, src/server.ts). Es el mostrador: recibe pedidos, responde y no cocina nada por su cuenta.

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    CoinGecko es la fuente

    Lo dispara: Backend solo

    CoinGecko publica el precio en USD de cada moneda con su fecha de actualización (last_updated_at). El worker lo consulta con COINGECKO_API_KEY, en lotes de hasta 50 ids, con timeout de 10 s y hasta 2 reintentos por llamada.

    MongoDB
    Ninguna: es un servicio externo.
    Código
    src/integrations/coingecko/coingecko.client.ts src/config/constants.ts
  2. 2

    El job poll-prices lo pide cada 10 minutos

    Lo dispara: Backend solo

    Con el cron */10 * * * * (UTC) el worker lee las monedas activas y pide sus precios. Si la corrida encuentra el lease ocupado, o no hay monedas activas, termina en skipped.

    MongoDB
    Lee coins (isActive: true); escribe job_locks.
    Código
    src/jobs/pollPrices.ts src/scheduler/adapters.ts
  3. 3

    Se inserta un snapshot en price_snapshots

    Lo dispara: Backend solo

    Por cada moneda cuyo sourceUpdatedAt es distinto del último guardado se inserta un snapshot con precio, capitalización, volumen y cambio 24 h. Las monedas sin dato nuevo se cuentan como omitidas. La colección es de series de tiempo y expira a los 90 días (SNAPSHOT_RETENTION_DAYS).

    MongoDB
    Lee el último sourceUpdatedAt por moneda; escribe price_snapshots.
    Código
    src/modules/snapshots/snapshots.service.ts src/db/ensureCollections.ts
  4. 4

    Se copia el último precio a coins.latest

    Lo dispara: Backend solo

    Para las monedas con snapshot nuevo, el worker actualiza coins.latest (solo si su capturedAt es más reciente que el guardado). Si esto falla, la corrida queda partial y los snapshots ya insertados se conservan.

    MongoDB
    Escribe coins.latest.
    Código
    src/modules/coins/coins.service.ts src/jobs/pollPrices.ts
  5. 5

    La corrida queda registrada en job_runs

    Lo dispara: Backend solo

    Cada corrida deja una fila con su trigger, estado, duración y contadores (coinsRequested, snapshotsInserted, skippedUnchanged, etc.). Se conservan 30 días.

    MongoDB
    Escribe job_runs.
    Código
    src/modules/job-runs/job-runs.service.ts
  6. 6

    GET /api/v1/coins lee precio actual, historial y estadísticas

    Lo dispara: Cliente

    El cliente pide la lista o el detalle y la API responde con coins.latest. /history (interval raw, 1h o 1d, opcional sma) y /stats (range 24h, 7d, 30d o 90d) leen price_snapshots. La watchlist también lee coins.latest. Nunca se llama a CoinGecko para servir estos datos.

    MongoDB
    Lee coins y price_snapshots.
    Código
    src/modules/coins/coins.routes.ts src/modules/snapshots/snapshots.service.ts src/modules/watchlist/watchlist.service.ts
  7. 7

    GET /api/v1/status resume la salud del worker

    Lo dispara: Cliente

    Devuelve activeCoins y, para poll-prices: lastRunAt, lastRunStatus, lastSuccessAt (última corrida success o partial), stale (verdadero si pasaron más de 30 minutos), nextRunAt y disabled. Los admins ven el detalle en /api/v1/admin/job-runs.

    MongoDB
    Lee job_runs, agenda_jobs y cuenta coins activas.
    Código
    src/modules/status/status.service.ts

Cómo verlo en tu entorno

  • Levanta lo básico: docker compose up (MongoDB como replica set y Mailpit), luego npm run dev (la API queda en http://localhost:3000) y, en otra terminal, npm run dev:worker.
  • Carga el catálogo con npm run seed:coins y luego espera una corrida (o ejecútala a mano con npm run job:poll-prices).
  • Postman: carpetas Coins (List coins (default), Coin detail), Price History, Price Stats y Status → Worker status.
  • GET /api/v1/status (Postman: carpeta Status, pedido Worker status) muestra activeCoins y, en pollPrices: lastRunAt, lastRunStatus, lastSuccessAt, stale, nextRunAt y disabled.
  • Logs del worker: en la terminal de npm run dev:worker aparecen líneas como Worker started, poll-prices run started / poll-prices run finished y send-notifications: sent.
  • Como admin: carpeta Admin - Job Runs → Job run detail muestra los contadores de una corrida concreta.
