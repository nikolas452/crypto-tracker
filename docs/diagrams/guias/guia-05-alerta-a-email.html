De un precio que cruza el umbral al correo en el buzón

Qué responde este diagrama: cómo se convierte un precio que cruza el umbral de una alerta en un correo entregado, con qué garantías y en qué momento se envía.

Idea clave: primero se "anota" el correo en una cola (outbox) dentro de la misma transacción que cambia la alerta, y después otro job lo envía. Así nunca hay una alerta disparada sin su correo anotado, ni dos correos por el mismo disparo.

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

Alerta
Una regla del usuario, por ejemplo "avisar si bitcoin baja de cierto precio". Vive en la colección alerts y tiene un estado (armed, triggered, completed, disabled).
Transacción
Un grupo de escrituras en MongoDB que se guardan todas o ninguna. Por eso MongoDB debe correr como replica set.
Outbox (cola de correos)
La colección notifications: una fila por correo pendiente. Se escribe junto con la alerta y otro proceso la vacía después.
dedupeKey
La clave única alertId:triggerCount de cada notificación. Impide crear dos correos para el mismo disparo.
Agenda
La librería que dispara los jobs a su hora. Guarda su agenda en la colección agenda_jobs de MongoDB y la revisa cada pocos segundos (AGENDA_PROCESS_EVERY, 10 s).
SMTP y Mailpit
SMTP es el protocolo de envío de correo. En local se usa Mailpit, un buzón de mentira: recibe por el puerto 1025 y se ve en http://localhost:8025.
Rearme (histéresis)
Una alerta disparada no vuelve a vigilar hasta que el precio se aleje del umbral en un porcentaje (rearmPct). Evita avisos repetidos por oscilaciones.

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    poll-prices entrega los precios nuevos a la evaluación

    Lo dispara: Backend solo

    Al terminar de guardar snapshots y coins.latest, poll-prices llama a evaluateAlerts con los valores de las monedas que tuvieron precio nuevo. Recorre con un cursor las alertas armed y triggered de esas monedas.

    MongoDB
    Lee alerts (coinId en las monedas con precio nuevo, status armed o triggered).
    Código
    src/jobs/pollPrices.ts src/jobs/alertEvaluation.ts
  2. 2

    Decidir qué hacer con cada alerta

    Lo dispara: Backend solo

    decide() devuelve TRIGGER (se cumple la condición y no está en cooldown), COOLDOWN (se cumple pero disparó hace menos de cooldownMinutes: no se escribe nada), REARM (una alerta triggered cuyo precio ya se alejó lo suficiente: vuelve a armed) o NOOP. Las condiciones son PRICE_ABOVE (precio mayor o igual), PRICE_BELOW (menor o igual) y CHANGE_24H_ABS_GTE (cambio 24 h en valor absoluto).

    MongoDB
    Lee alerts; con REARM escribe alerts.
    Código
    src/modules/alerts/alerts.decide.ts
  3. 3

    Abrir la transacción y cambiar el estado de la alerta

    Lo dispara: Backend solo

    Con TRIGGER se abre una transacción de MongoDB. Primero actualiza la alerta con control de versión: armed pasa a triggered (o a completed si su modo es once) y suma 1 a triggerCount. Si otro proceso la cambió mientras tanto, no se escribe nada y se cuenta un conflicto.

    MongoDB
    Escribe alerts (status, lastTriggeredAt, lastTriggeredValue, version, triggerCount).
    Código
    src/jobs/alertEvaluation.ts
  4. 4

    Verificar al usuario

    Lo dispara: Backend solo

    Dentro de la misma transacción lee al usuario. Si no existe, no tiene email o no está verificado, se revierte todo y la alerta sigue armed.

    MongoDB
    Lee users.
    Código
    src/jobs/alertEvaluation.ts
  5. 5

    Anotar la notificación pending en la outbox

    Lo dispara: Backend solo

    Inserta en notifications una fila pending con el destinatario, un payload congelado (moneda, tipo, umbral, valor, precio) y la clave dedupeKey alertId:triggerCount, que es única. Si esa clave ya existía, se aborta la transacción para no duplicar el correo. Cualquier otro fallo de escritura revierte todo y degrada la corrida a partial.

    MongoDB
    Escribe notifications (status: "pending", attempts: 0, maxAttempts: 5).
    Código
    src/jobs/alertEvaluation.ts src/modules/notifications/notifications.model.ts
  6. 6

    Commit o rollback

    Lo dispara: Backend solo

    Si las tres escrituras salieron bien se confirma la transacción (alertsTriggered suma 1); si no, se revierte completa. No existe el estado intermedio "alerta disparada sin correo anotado".

    MongoDB
    Confirma o revierte los cambios en alerts y notifications.
    Código
    src/jobs/alertEvaluation.ts
  7. 7

    Despertar a send-notifications

    Lo dispara: Backend solo

    Si la corrida no fue failed y hubo al menos un disparo, poll-prices encola send-notifications con agenda.now. Si no hubo disparos, el envío lo hace el cron de cada minuto (* * * * *).

    MongoDB
    Escribe agenda_jobs.
    Código
    src/jobs/pollPrices.ts src/worker.ts
  8. 8

    Reclamar la notificación

    Lo dispara: Backend solo

    send-notifications reclama de forma atómica la próxima pending con nextAttemptAt vencido; queda sending con lockedBy del worker. Si el usuario ya no existe, la marca cancelled.

    MongoDB
    Escribe notifications (pending → sending); lee users.
    Código
    src/jobs/sendNotifications.ts src/modules/notifications/notifications.service.ts
  9. 9

    Enviar el correo por SMTP

    Lo dispara: Backend solo

    Renderiza la plantilla alert-triggered (asunto, texto y HTML, con hora UTC y hora local de referencia) y la envía por SMTP. En local, Mailpit lo recibe en el puerto 1025 y lo muestra en http://localhost:8025.

    MongoDB
    Ninguna en el envío.
    Código
    src/modules/notifications/templates/alert-triggered.ts src/integrations/mailer/smtpMailer.ts
  10. 10

    Registrar el resultado

    Lo dispara: Backend solo

    Si el SMTP acepta: sent con sentAt. Si falla de forma transitoria: vuelve a pending con espera de 1, 5, 15 o 60 minutos. Si el rechazo es permanente (SMTP_REJECTED) o ya hubo 5 intentos: failed.

    MongoDB
    Escribe notifications (sent, pending con nuevo nextAttemptAt, o failed).
    Código
    src/jobs/sendNotifications.ts src/integrations/mailer/mailer.errors.ts

Cómo verlo en tu entorno

  • Levanta lo básico: docker compose up (MongoDB como replica set y Mailpit), luego npm run dev (la API queda en http://localhost:3000) y, en otra terminal, npm run dev:worker.
  • Crea una alerta con My Alerts → Create a PRICE_BELOW alert (Postman) o el pedido equivalente de requests.http. La cuenta debe tener el email verificado.
  • Provoca la evaluación: Admin - Jobs → Trigger a job now con poll-prices, o espera la próxima corrida. La condición debe cumplirse con un precio nuevo de CoinGecko.
  • Mailpit: abre http://localhost:8025 para ver los correos que envía el worker (recibe por SMTP en el puerto 1025).
  • Revisa el resultado: My Alerts → Alert detail (estado triggered o completed, triggerCount) y My Notifications → List my notification history. Como admin: Admin - Notifications → List notifications (full diagnostic detail).
  • Logs del worker: en la terminal de npm run dev:worker aparecen líneas como Worker started, poll-prices run started / poll-prices run finished y send-notifications: sent.
