Estados de una alerta de precio

Qué responde este diagrama: en qué estados puede estar una alerta, qué la hace cambiar de uno a otro y cuáles de esos cambios los pide el cliente y cuáles ocurren solos.

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

Alerta
Una regla del usuario, por ejemplo "avisar si bitcoin baja de cierto precio". Vive en la colección alerts y tiene un estado (armed, triggered, completed, disabled).
Rearme (histéresis)
Una alerta disparada no vuelve a vigilar hasta que el precio se aleje del umbral en un porcentaje (rearmPct). Evita avisos repetidos por oscilaciones.
Worker
El programa que trabaja por reloj (npm run dev:worker, src/worker.ts). Es la cocina: nadie le pide nada, prepara las cosas solo. No tiene servidor HTTP.
Cliente
Cualquier programa que llame a la API: una web, una app o Postman. En este proyecto todavía no hay front end.

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    Creada → armed

    Lo dispara: Cliente

    El cliente hace POST /api/v1/me/alerts. La alerta nace armed, sin evaluar. Valores por defecto: mode: "recurring", cooldownMinutes: 60 y rearmPct: 1. El tipo (PRICE_ABOVE, PRICE_BELOW o CHANGE_24H_ABS_GTE) no se puede cambiar después.

    MongoDB
    Escribe alerts.
    Código
    src/modules/alerts/alerts.service.ts src/modules/alerts/alerts.model.ts
  2. 2

    armed → triggered (modo recurring)

    Lo dispara: Backend solo

    En una corrida de poll-prices con precio nuevo, si la condición se cumple y no hay cooldown, la alerta pasa a triggered y se anota su correo. Condiciones (inclusivas): PRICE_ABOVE precio mayor o igual al umbral; PRICE_BELOW menor o igual; CHANGE_24H_ABS_GTE cambio 24 h en valor absoluto mayor o igual.

    MongoDB
    Escribe alerts y notifications (transacción).
    Código
    src/jobs/alertEvaluation.ts src/modules/alerts/alerts.decide.ts
  3. 3

    armed → completed (modo once)

    Lo dispara: Backend solo

    Igual que el paso anterior, pero si el modo es once la alerta termina en completed y ya no se vuelve a evaluar (salvo que el cliente la reactive).

    MongoDB
    Escribe alerts y notifications (transacción).
    Código
    src/jobs/alertEvaluation.ts
  4. 4

    Cooldown: sigue armed

    Lo dispara: Backend solo

    Si la condición se cumple pero la alerta disparó hace menos de cooldownMinutes, no pasa nada: no se escribe ni siquiera lastEvaluatedAt. Sigue armed.

    MongoDB
    Sin escrituras.
    Código
    src/modules/alerts/alerts.decide.ts
  5. 5

    triggered → armed (rearme automático)

    Lo dispara: Backend solo

    Una alerta triggered vuelve a armed cuando el precio se aleja del umbral en rearmPct % (PRICE_ABOVE: precio menor que umbral × (1 − rearmPct/100); PRICE_BELOW: mayor que umbral × (1 + rearmPct/100)). Para CHANGE_24H_ABS_GTE el cambio absoluto debe bajar de umbral − rearmPct.

    MongoDB
    Escribe alerts.
    Código
    src/modules/alerts/alerts.decide.ts src/jobs/alertEvaluation.ts
  6. 6

    triggered → armed (el cliente cambia el umbral)

    Lo dispara: Cliente

    PATCH /api/v1/me/alerts/:id con un nuevo threshold sobre una alerta triggered la rearma sin esperar. No reinicia lastTriggeredAt ni triggerCount.

    MongoDB
    Escribe alerts (status, version).
    Código
    src/modules/alerts/alerts.service.ts
  7. 7

    Apagar: cualquier estado → disabled

    Lo dispara: Cliente

    PATCH con enabled: false deja la alerta en disabled, sin importar en qué estado estaba. Una alerta disabled nunca se evalúa.

    MongoDB
    Escribe alerts.
    Código
    src/modules/alerts/alerts.service.ts
  8. 8

    Reactivar: disabled o completed → armed

    Lo dispara: Cliente

    PATCH con enabled: true sobre una alerta disabled o completed la vuelve a armed, siempre que el usuario no haya llegado al tope de ALERTS_MAX_ACTIVE (20 alertas activas entre armed y triggered; si no, 422 LIMIT_REACHED).

    MongoDB
    Lee y escribe alerts.
    Código
    src/modules/alerts/alerts.service.ts
  9. 9

    Borrar la alerta

    Lo dispara: Cliente

    DELETE /api/v1/me/alerts/:id responde siempre 204. Si la alerta existía y era del usuario, se borra y sus notificaciones pending pasan a cancelled.

    MongoDB
    Borra en alerts; escribe notifications.
    Código
    src/modules/alerts/alerts.service.ts src/modules/notifications/notifications.service.ts

Cómo verlo en tu entorno

  • Levanta lo básico: docker compose up (MongoDB como replica set y Mailpit), luego npm run dev (la API queda en http://localhost:3000) y, en otra terminal, npm run dev:worker.
  • Importa crypto-tracker.postman_collection.json en Postman (variable baseUrl) o abre requests.http con la extensión REST Client de VS Code; ambos traen los mismos pedidos. Carpeta My Alerts: Create a PRICE_BELOW alert, Alert detail, Disable an alert, Re-enable an alert, Change threshold (re-arms if triggered) y Delete an alert.
  • Observa cada cambio de estado con List my alerts - filtered by status and coin (?status=armed,triggered).
  • Para ver un disparo: crea una alerta con una condición que ya se cumpla, dispara poll-prices (Admin - Jobs → Trigger a job now) y vuelve a consultar el estado. Recuerda que solo se evalúan las monedas con precio nuevo en esa corrida.
  • Mailpit: abre http://localhost:8025 para ver los correos que envía el worker (recibe por SMTP en el puerto 1025).
