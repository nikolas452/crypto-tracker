Línea de tiempo de una alerta: del pedido del cliente al correo

Qué responde este diagrama: qué pasa, en orden y con horas de ejemplo, desde que el cliente crea una alerta hasta que llega el correo, y qué mensajes los pide el cliente y cuáles ocurren solos por reloj.

Cómo leer el diagrama: cada mensaje lleva una letra. C es "pedido por el cliente" (hay una petición HTTP) y R es "solo, por reloj" (el worker actúa sin que nadie pida nada). Las horas (10:00, 10:07, 10:10) son un ejemplo ilustrativo: en la realidad poll-prices corre cada 10 minutos y Agenda puede demorar hasta unos 10 segundos.

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

Cliente
Cualquier programa que llame a la API: una web, una app o Postman. En este proyecto todavía no hay front end.
API
El programa que atiende pedidos HTTP (npm run dev, src/server.ts). Es el mostrador: recibe pedidos, responde y no cocina nada por su cuenta.
Worker
El programa que trabaja por reloj (npm run dev:worker, src/worker.ts). Es la cocina: nadie le pide nada, prepara las cosas solo. No tiene servidor HTTP.
MongoDB
La base de datos. Es el único lugar donde se encuentran API y worker: el worker deja cosas ahí y la API las lee.
Alerta
Una regla del usuario, por ejemplo "avisar si bitcoin baja de cierto precio". Vive en la colección alerts y tiene un estado (armed, triggered, completed, disabled).
Transacción
Un grupo de escrituras en MongoDB que se guardan todas o ninguna. Por eso MongoDB debe correr como replica set.
Outbox (cola de correos)
La colección notifications: una fila por correo pendiente. Se escribe junto con la alerta y otro proceso la vacía después.
dedupeKey
La clave única alertId:triggerCount de cada notificación. Impide crear dos correos para el mismo disparo.
SMTP y Mailpit
SMTP es el protocolo de envío de correo. En local se usa Mailpit, un buzón de mentira: recibe por el puerto 1025 y se ve en http://localhost:8025.

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    10:00 · C1 a C3: el cliente crea la alerta y la petición termina

    Lo dispara: Cliente

    El cliente envía POST /api/v1/me/alerts con token. La API comprueba email verificado, moneda activa y tope de alertas, guarda la alerta como armed (por defecto mode: recurring, cooldownMinutes: 60, rearmPct: 1) y responde 201. No evalúa nada y no toca a CoinGecko: ahí termina el trabajo de la API. El cliente puede irse.

    MongoDB
    Escribe una fila en alerts con status: "armed". Lee coins (para validar y calcular conditionCurrentlyMet).
    Código
    src/modules/alerts/alerts.service.ts src/modules/alerts/alerts.routes.ts
  2. 2

    10:07 · el precio cruza el umbral y nadie lo nota

    Lo dispara: Backend solo

    El precio cambia en CoinGecko, pero en este sistema no corre nada que lo esté mirando: el worker solo mira cada 10 minutos y la API no evalúa alertas. Por eso el diagrama no dibuja mensajes en ese tramo: es una espera, no una acción.

    MongoDB
    Nada cambia todavía en MongoDB.
    Código
    src/scheduler/definitions.ts src/config/constants.ts
  3. 3

    10:10 · R1: poll-prices pide precios a CoinGecko

    Lo dispara: Backend solo

    Llega la hora de */10 * * * *. Agenda dispara poll-prices, que toma el lease, abre su fila en job_runs, lee las monedas activas y pide todos los precios a CoinGecko.

    MongoDB
    Lee coins; escribe job_locks y job_runs (running).
    Código
    src/jobs/pollPrices.ts src/scheduler/adapters.ts
  4. 4

    10:10 · R2: guarda snapshot y latest

    Lo dispara: Backend solo

    Por cada moneda cuyo sourceUpdatedAt cambió, inserta un snapshot y actualiza coins.latest. Las monedas sin dato nuevo se omiten y, importante, no se evalúan sus alertas en esta corrida.

    MongoDB
    Escribe price_snapshots y coins.latest.
    Código
    src/jobs/pollPrices.ts src/modules/coins/coins.service.ts
  5. 5

    10:10 · R3: evalúa las alertas y prepara el correo en una transacción

    Lo dispara: Backend solo

    Recorre las alertas armed y triggered de las monedas con precio nuevo. Para cada una, decide() devuelve TRIGGER, REARM, COOLDOWN o NOOP. Con TRIGGER abre una transacción de MongoDB que hace tres cosas: actualiza la alerta (armed pasa a triggered, o a completed si es once) con control de versión, verifica que el usuario exista y tenga email verificado, e inserta una notificación pending con dedupeKey alertId:triggerCount. Si algo falla (conflicto de versión, usuario sin email verificado, clave duplicada) se revierte todo y la alerta queda como estaba.

    MongoDB
    Lee alerts y users. Escribe alerts y notifications (pending) en una sola transacción.
    Código
    src/jobs/alertEvaluation.ts src/modules/alerts/alerts.decide.ts
  6. 6

    10:10 · R4: agenda.now despierta a send-notifications

    Lo dispara: Backend solo

    Si la corrida no terminó en failed y disparó al menos una alerta, poll-prices encola send-notifications con agenda.now (fire-and-forget: no espera su resultado). Si no disparó ninguna, el envío queda para el cron de cada minuto. Agenda lo toma en su próximo ciclo de revisión (hasta unos 10 s).

    MongoDB
    Escribe agenda_jobs (un documento puntual con trigger: "agenda").
    Código
    src/jobs/pollPrices.ts src/worker.ts
  7. 7

    10:10 · R5 y R6: reclama la pending y envía el correo

    Lo dispara: Backend solo

    send-notifications reclama de forma atómica la notificación pending (pasa a sending), comprueba que el usuario exista, renderiza la plantilla alert-triggered y la envía por SMTP (en local, a Mailpit). El correo llega al buzón del usuario sin que ningún cliente lo haya pedido.

    MongoDB
    Lee y escribe notifications (pending → sending); lee users.
    Código
    src/jobs/sendNotifications.ts src/modules/notifications/templates/alert-triggered.ts src/integrations/mailer/smtpMailer.ts
  8. 8

    10:10 · R7: marca la notificación como sent

    Lo dispara: Backend solo

    Si el SMTP acepta el mensaje, la fila pasa a sent con sentAt y providerMessageId. Si falla de forma transitoria vuelve a pending con espera (1, 5, 15, 60 min); si el rechazo es permanente (SMTP_REJECTED) o se agotan los 5 intentos, queda failed. Cierra su fila en job_runs.

    MongoDB
    Escribe notifications (sent, failed o de vuelta a pending) y job_runs.
    Código
    src/jobs/sendNotifications.ts src/jobs/notifyBackoff.ts
  9. 9

    Después · C4 a C6: el cliente consulta sus notificaciones

    Lo dispara: Cliente

    No hay push. Si el cliente quiere saber qué pasó, pide GET /api/v1/me/notifications (opcionalmente ?status=sent). La API lee las filas del usuario ordenadas de la más nueva a la más vieja y las devuelve con status, to (enmascarado), payload, attempts, sentAt y lastError.

    MongoDB
    Solo lee notifications filtrando por el userId del token.
    Código
    src/modules/notifications/notifications.service.ts src/modules/notifications/notifications.routes.ts

Cómo verlo en tu entorno

  • Levanta lo básico: docker compose up (MongoDB como replica set y Mailpit), luego npm run dev (la API queda en http://localhost:3000) y, en otra terminal, npm run dev:worker.
  • Importa crypto-tracker.postman_collection.json en Postman (variable baseUrl) o abre requests.http con la extensión REST Client de VS Code; ambos traen los mismos pedidos.
  • Paso a paso con Postman: (1) carpeta Auth (Firebase) → Sign in (get ID token); (2) My Alerts → Create a PRICE_BELOW alert (el email de la cuenta debe estar verificado); (3) espera a la próxima corrida o usa Admin - Jobs → Trigger a job now con poll-prices (solo encola; la ejecuta el worker); (4) mira los logs del worker y Mailpit; (5) My Notifications → List my notification history.
  • Para que la alerta dispare, su condición debe cumplirse en una corrida en la que la moneda tenga un precio nuevo de CoinGecko. Si el precio de la fuente no cambió desde la corrida anterior, esa moneda se omite y su alerta no se evalúa.
  • Mailpit: abre http://localhost:8025 para ver los correos que envía el worker (recibe por SMTP en el puerto 1025).
  • Logs del worker: en la terminal de npm run dev:worker aparecen líneas como Worker started, poll-prices run started / poll-prices run finished y send-notifications: sent.
