Qué atraviesa un request antes de llegar al handler

Qué responde este diagrama: por qué pasos fijos viaja cada pedido HTTP dentro de la API, en qué orden, y cómo termina cuando algo sale mal.

Idea clave: es la cola del mostrador. Cada pedido pasa por los mismos controles, en el mismo orden, y cualquier error termina en un único manejador que lo convierte en un JSON uniforme. El orden real está fijado en createApp().

El diagrama

Abrir el diagrama a pantalla completa. Los textos fijos del visor (botones y leyenda) están en inglés; el contenido del diagrama está en español.

Mini glosario

Middleware
Un paso por el que pasa cada pedido antes de llegar a su handler (identificar, limitar, autenticar). Se ejecutan en un orden fijo definido en src/app.ts.
Handler
La función que resuelve un endpoint concreto una vez que pasó todos los middlewares.
Límite de tasa
Un tope de pedidos por ventana de tiempo. Si se supera, la API responde 429 RATE_LIMITED.
Token de Firebase (JWT)
La credencial que el cliente obtiene de Firebase Auth y envía en Authorization: Bearer <token>. La API lo verifica con Firebase.
Cliente
Cualquier programa que llame a la API: una web, una app o Postman. En este proyecto todavía no hay front end.

Paso a paso

Cada paso indica quién lo dispara: el Cliente (alguien hace un pedido HTTP), el Backend solo (el worker actúa por reloj, sin que nadie pida nada) o Ambos. Los nombres de rutas, jobs, estados, colecciones y variables son los reales del código.

  1. 1

    Llega el request

    Lo dispara: Cliente

    Express recibe el pedido. Antes de todo se configura trust proxy con TRUST_PROXY (0 en desarrollo, 1 en producción) para que el límite por IP identifique al cliente real y no al proxy.

    MongoDB
    Ninguna.
    Código
    src/app.ts
  2. 2

    Identificación y log

    Lo dispara: Cliente

    requestId toma el encabezado X-Request-Id del cliente (si es válido, hasta 128 caracteres) o genera un UUID, y lo devuelve en la respuesta. Después el log de requests (pino-http) registra el pedido con ese id.

    MongoDB
    Ninguna.
    Código
    src/middlewares/requestId.ts src/middlewares/requestLogger.ts
  3. 3

    Cabeceras de seguridad y cuerpo JSON

    Lo dispara: Cliente

    helmet agrega cabeceras de seguridad y express.json lee el cuerpo con un tope de 100 KB. Un JSON mal formado responde 400 VALIDATION_ERROR y uno demasiado grande, 413.

    MongoDB
    Ninguna.
    Código
    src/app.ts src/middlewares/errorHandler.ts
  4. 4

    /health y /health/ready, antes del límite

    Lo dispara: Cliente

    Las rutas de salud se montan antes del limitador, así que nunca cuentan contra el tope. /health no toca la base; /health/ready comprueba MongoDB y responde 503 si no está disponible.

    MongoDB
    /health/ready hace un chequeo de conectividad a MongoDB.
    Código
    src/routes/health.routes.ts src/lib/health.ts
  5. 5

    Límite por IP en /api

    Lo dispara: Cliente

    Todo lo que empieza con /api pasa por un limitador de 300 pedidos por 15 minutos por IP (RATE_LIMIT_MAX, RATE_LIMIT_WINDOW_MIN). Si se supera: 429 RATE_LIMITED.

    MongoDB
    Ninguna (el contador vive en memoria del proceso de la API).
    Código
    src/middlewares/rateLimiter.ts
  6. 6

    Ruteo por prefijo: pública, de usuario o de administrador

    Lo dispara: Cliente

    /api/v1/coins lleva Cache-Control: public, max-age=60 y /api/v1/status lleva no-store; ambas son públicas. /me, /me/watchlist, /me/alerts y /me/notifications exigen requireAuth y un límite por usuario de 120 pedidos por minuto (USER_RATE_LIMIT_PER_MIN); las tres últimas llevan Cache-Control: private, no-cache. /api/v1/admin lleva no-store, requireAuth con checkRevoked: true, el mismo límite por usuario y por último requireRole('admin'): sin rol admin, 403 FORBIDDEN.

    MongoDB
    Las rutas autenticadas leen/escriben users (perfil del token).
    Código
    src/app.ts src/middlewares/requireAuth.ts src/middlewares/requireRole.ts src/middlewares/cacheControl.ts
  7. 7

    El handler resuelve el pedido

    Lo dispara: Cliente

    Cada ruta valida entrada con zod (por ejemplo, un parámetro de query desconocido responde 400 VALIDATION_ERROR), llama al servicio del módulo y responde. La respuesta sale directo al cliente.

    MongoDB
    Depende del módulo (ver guía 09).
    Código
    src/modules/*/*.routes.ts
  8. 8

    Sin coincidencia: 404. Con error: errorHandler

    Lo dispara: Cliente

    Si ninguna ruta coincide, notFoundHandler genera 404 NOT_FOUND. Cualquier error (de validación, de autenticación o inesperado) termina en errorHandler, que responde siempre con la misma forma: { "error": { "code", "message", "requestId", "details"? } }. Un error no previsto responde 500 INTERNAL_ERROR y en desarrollo agrega el stack.

    MongoDB
    Ninguna.
    Código
    src/middlewares/notFoundHandler.ts src/middlewares/errorHandler.ts src/lib/errors.ts

Cómo verlo en tu entorno

  • Con la API levantada (npm run dev), prueba en Postman la carpeta Health: Liveness with X-Request-Id (mira que la respuesta devuelva el mismo X-Request-Id), Unknown route -> 404 y Malformed JSON body -> 400.
  • Prueba la autenticación por prefijo: Me → Get my profile - no token -> 401 y Admin - Job Runs → List job runs - non-admin token -> 403.
  • Mira el log de la API: cada pedido aparece con su requestId, el mismo que viaja en la respuesta y en el error.
  • Importa crypto-tracker.postman_collection.json en Postman (variable baseUrl) o abre requests.http con la extensión REST Client de VS Code; ambos traen los mismos pedidos.
